# Avatar Video Automation

Built from a real multi-round project: a daily status-briefing video pulling from a few local data sources, narrated by a custom HeyGen avatar and delivered by email on a Windows scheduled task. Two halves: generating a good custom avatar/voice, and making a headless scheduled run actually work. Most projects in this space need both, but either can apply alone.

## Part 1: Generating a custom HeyGen avatar/voice

**The stock lookpacks are limited — know when to go custom.** HeyGen's avatar groups ship with a handful of lookpacks (Office, Corporate, Studio Streamer, Livingroom, etc.) across broadly similar photoreal human avatars. If the user wants something those packs don't cover — a hologram, a stylized character, anything non-photoreal — don't keep cycling through existing lookpacks hoping one fits. Generate a new one.

**`create_prompt_avatar` generates a new identity from text; `create_image_generation` does not.** `create_image_generation` only does `identity_remix` — it needs existing photos of a person plus a reference image to copy style from. It cannot invent a new concept from a blank description; its own schema says so. If the ask is "a new generic hologram look" rather than "take this photo and restyle it," go straight to `create_prompt_avatar`.

**Keep `create_prompt_avatar` prompts short.** A ~180-word prompt describing clothing down to the seam lines failed outright (500 / tool_execution_error) twice in a row. Trimming the same content to ~85 words succeeded on the first try. If a long, highly-detailed prompt fails, don't assume the content was the problem — shorten it first and keep the same intent.

**Always download and actually look at the generated image before deciding anything.** Don't judge a generated avatar from its name or your own expectation of what the prompt should produce. Pull the actual image (and, once animated, the actual rendered video thumbnail) and look at it. This caught a real nudity issue (a translucent/glowing body with no clothing implied) and confirmed a "circuit pattern on skin" concept actually read as eerie rather than friendly — neither was obvious from the prompt text alone.

**Watch for unintended nudity in generated humanoid/stylized avatars.** A prompt describing a glowing, translucent, or wireframe-patterned body can render as effectively nude even with no sexual intent in the prompt, because "translucent skin with a light pattern" and "clothing" aren't the same instruction. If the avatar will be shown to anyone or run repeatedly (not a one-off private test), check for this explicitly and iterate on the prompt (add explicit clothing — a bodysuit, collar, seams, etc.) rather than shipping the first result.

**If a reference image is a specific recognizable fictional character (not just a style), that's an IP/trademark issue — redirect to the genre, not the character.** If someone points at a picture of e.g. a game or movie character and says "make it look like this," distinguish *this specific design* (a trademarked character's exact face, markings, color scheme) from *the aesthetic the reference is pulling from* (e.g. "blue holographic AI assistant" as a sci-fi genre convention). Build toward the genre — different pose, different face, no franchise-specific markings — especially when the avatar will render repeatedly/permanently rather than as a one-off. Say this plainly to the user rather than quietly complying or quietly refusing; it's usually an easy redirect once named.

**Test animation/lip-sync on the specific avatar_id separately, before running it against the real script.** A fresh `create_prompt_avatar` identity being speakable isn't guaranteed by the still image looking right — confirm with a short throwaway test line via `create_video_from_avatar` first. This also avoids burning a full real-script render (which costs more and takes longer) on an avatar that turns out not to animate well.

**A long "processing" status is not proof something is stuck.** Avatar and video generation can sit in `processing` for 40+ minutes with no error set, then resolve fine. Before assuming it's broken and retrying (which risks creating duplicate/orphaned generations and doubles cost), check whether the record exposes its own timestamps (e.g. a video's `created_at`/`completed_at`) — more than one "stuck" render turned out to be ~100 seconds of real render time plus a long queue/polling wait, not an actual hang. If there's truly no error field and no way to check real elapsed render time, give it a generous explicit time budget (e.g. "stop and report if still processing after 60-75 minutes total") rather than polling forever or retrying reflexively.

## Part 2: Running it headlessly and on a schedule

The goal: a Claude Code prompt that gathers data, maybe generates a HeyGen video, and delivers a result — triggered by a Windows Scheduled Task (or equivalent) instead of a human typing into an interactive session. This surfaces problems that never show up in an interactive session, because an interactive session has a human to approve tool prompts and runs from a working directory a human chose.

**Pass long prompts via stdin, never as a `-p` command-line argument.** `claude.exe -p "$longPromptString"` truncates silently once the prompt is long enough to hit Windows' command-line length limit — there's no error, just a cut-off prompt, and the model will often reply asking where the rest of the message is (which looks like a content problem, not a plumbing one, until you notice the reply is confused about where the prompt stops). Pipe it instead: `Get-Content $promptFile -Raw | & claude.exe -p --model sonnet --permission-mode default`.

**A headless run must `cd` into the project directory before launching Claude Code, or it silently loses the project's own permissions.** If the runner script launches `claude.exe` from some other working directory (e.g. the scheduled task's default), Claude Code falls back to user-level settings only and misses the project's own `.claude/settings.json` — including tools that are *already* allow-listed there. The symptom is confusing: an already-allowed tool gets denied with no obvious reason, because nothing says "wrong settings file loaded." Add `Set-Location <project-dir>` (or the shell equivalent) as the first real step in the runner script.

**Log output encoding matters.** Redirecting a headless Claude Code run's output with PowerShell's default encoding can produce garbled, spaced-out text when the log is read back with a different tool (e.g. `cat`/`grep` in a different shell) — each character separated by a space, which looks like real model output gone wrong but is actually a UTF-16-vs-UTF-8 mismatch. Force UTF-8 explicitly when writing the log (e.g. `Out-File -Append -Encoding utf8`).

**Editing a project's own `.claude/settings.json` permissions, or anything that looks like granting a session more capability or persistence, is blocked by a safety classifier — and that block cannot be talked past.** Attempting to add a tool to the `permissions.allow` array (or similarly, registering certain kinds of persistence) gets refused as "Self-Modification" / "Unauthorized Persistence," by an agent *and* by the orchestrating session itself, even when the human explicitly says "do it anyway" or "outside auto mode" in chat. That verbal instruction does not change the session's actual permission mode — it's a harness-level control, not a conversational one. The only real path forward: the human edits the file directly themselves, outside of any Claude Code tool call entirely (a plain text editor is enough), or changes their actual Claude Code permission-mode setting through the real settings mechanism (not by telling an agent to ignore it). Don't retry this through a different tool (Bash instead of Edit, etc.) — that's routing around an intentional safety gate, not a legitimate workaround. Registering a scheduled task itself was *not* blocked in practice — the wall is specifically around self-modifying permissions/config, not task scheduling in general.

**Verify the actual available tool names for the headless context — don't assume they match the interactive session's.** A headless run tied to a different account/connector setup can expose different MCP tool names for "the same" service than the interactive session the prompt was originally written and tested in (e.g. an account-level connector namespace vs. a separately-installed plugin's namespace). Confirm by reading the actual denied-tool-call error from a real headless test run, or by checking the relevant config file (e.g. `.claude.json`'s per-project `mcpServers`/`enabledMcpjsonServers` and the account's connector list) — don't trust a model's self-report about what's available without checking, and don't carry over tool names from the interactive-session version of the prompt unverified.

**A cloud-based scheduled-agent routine and a local scheduled task have a real freshness tradeoff — pick based on data, not convenience.** A cloud routine (sandboxed, no local filesystem access) is simpler to set up, but if the task depends on a locally-edited file (a git-backed vault, a local database) that only syncs to a remote source on some cadence (e.g. a nightly backup push), the cloud routine will only ever see that last sync point — stale by up to a full day for a same-day task. If the task needs live, same-day local state, use a local scheduled task (Windows Task Scheduler / cron) that can actually read the live filesystem, even though it's a different, slightly more manual setup path than a cloud-routine skill might offer by default.

**Verify end-to-end with a real trigger, not just "the task object was created."** `Register-ScheduledTask` succeeding only proves the task exists — it says nothing about whether the underlying script, prompt, or permissions actually work. Trigger it by hand (`Start-ScheduledTask`) and read the real log output / check for the real downstream effect (an email that actually arrived, a file that actually changed) before considering the automation done.
